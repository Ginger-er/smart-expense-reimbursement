### 1.2 识别结果校验管道

```java
// 责任链模式，每个校验器独立可测试
public interface InvoiceValidator {
    ValidateResult validate(InvoiceOcrResult ocrResult, Long tripId);
    int order(); // 执行顺序
}

// 校验器链
1. AmountConsistencyValidator   (order=1)  // 金额=明细求和
2. DateValidityValidator         (order=2)  // 日期≤今天
3. InvoiceCodeValidator          (order=3)  // 发票代码校验位
4. DuplicateDetectValidator      (order=4)  // 重复报销检测（直接拦截）
5. TripDateRangeValidator        (order=5)  // 日期在出差范围内
```

**设计要点**：
- 校验器1-3失败 → 标记"校验失败"，允许人工确认
- 校验器4失败 → **直接拦截**，返回错误 "该发票已报销"
- 校验器5失败 → 标记"异常"，需填写说明

### 1.3 OCR 调用容错设计

```
调用策略：
1. 超时：连接超时3s，读取超时5s
2. 重试：失败后重试1次，间隔500ms
3. 熔断：使用 Resilience4j CircuitBreaker
   - 滑动窗口10次
   - 失败率阈值50%
   - 熔断后30s自动恢复
   - 熔断期间直接走降级→手动填写
4. 降级：返回 null → 前端展示手动填写表单
5. 监控：每次调用记录耗时、结果到 ai_invoke_log
```

## 二、审批流引擎——Camunda 集成细节

### 2.1 BPMN 流程定义

审批节点配置（不是硬编码，是 BPMN XML）：

```
流程变量：
- amount: 报销金额（用于条件分支判断）
- skipPrevious: 驳回重提时是否跳过已通过节点
- currentLevel: 当前审批层级（1-3）

条件分支表达式：
- 金额 < 1000: ${amount < 1000}
- 1000 ≤ 金额 < 5000: ${amount >= 1000 && amount < 5000}
- 金额 ≥ 5000: ${amount >= 5000}
```

### 2.2 审批操作与 Camunda 交互

```java
@Service
public class ApprovalService {

    // 提交报销单 → 启动流程
    public void startProcess(Reimbursement reimbursement) {
        Map<String, Object> variables = Map.of(
            "amount", reimbursement.getTotalAmount(),
            "skipPrevious", false,
            "currentLevel", 1
        );
        ProcessInstance instance = runtimeService
            .startProcessInstanceByKey("reimbursement-approval",
                reimbursement.getReimburseNo(), variables);
        reimbursement.setCamundaInstanceId(instance.getId());
    }

    // 审批通过 → 完成任务 → 流程自动流转到下一节点
    public void approve(String taskId, String comment) {
        taskService.createTaskQuery().taskId(taskId).singleResult();
        taskService.complete(taskId, Map.of("approved", true, "comment", comment));
    }

    // 审批驳回 → 终止流程 → 状态回退
    public void reject(String instanceId, String reason) {
        runtimeService.deleteProcessInstance(instanceId, reason);
        // 更新 reimbursement.status = 4 (已驳回)
    }
}
```

### 2.3 驳回重提边界场景

| 场景 | 处理方式 |
|------|----------|
| 第一级驳回 | 直接终止，重新从第一级开始 |
| 第二级驳回（第一级已通过） | 终止旧实例 → 新实例启动时设置 skipLevel1=true → 直接跳到第二级 |
| 第三级驳回（前两级已通过） | 同理，skipLevel1+skipLevel2=true → 直接跳到第三级 |
| 同一审批人多次驳回 | 审批记录表保留所有历史，展示"第N次提交" |

### 2.4 Camunda 监控指标

```
- 待审批任务数 → /camunda/task/count
- 平均审批耗时 → 从流程启动到结束的时间
- 各节点驳回率 → 哪个审批节点驳回最多
- 超时未审批任务 → 超过24小时未处理的
```

## 三、异常预警——规则引擎实现

### 3.1 规则抽象

```java
public interface AbnormalRule {
    String getCode();        // 规则编码 A001-A005
    String getName();        // 规则名称
    RiskLevel getLevel();   // 风险等级 HIGH/MEDIUM/LOW

    // 核心方法：检查报销单是否命中规则
    Optional<AbnormalHit> check(Reimbursement reimbursement);

    // 按 order() 排序执行，耗时长的规则放后面
    int order();
}

// 每条规则一个实现类，职责单一
// A001AmountSurgeRule      → 查询同员工同类型上月金额 → 对比
// A002LimitBorderRule      → 查询费用标准 → 对比90%阈值
// A003DuplicateInvoiceRule → 查询同发票号是否已报销
// A004DateMismatchRule     → 对比发票日期与出差日期
// A005HighFrequencyRule    → 查询最近7天报销次数
```

### 3.2 规则执行策略

```
执行顺序：A003(重复发票,拦截级) → A004(日期) → A001(金额) → A002(限额) → A005(频率)

优化：
- A003 用 EXISTS 子查询，有索引，极快
- A001 需要聚合计算，走 Redis 缓存的月度统计
- 命中高风险的规则后，后续低风险规则继续执行（不短路）—— 一个报销可能触发多条异常
```

### 3.3 定时任务 XXL-Job Handler

```java
@XxlJob("expenseAbnormalScanHandler")
public void execute() {
    // 1. 获取昨日提交/通过的报销单
    List<Reimbursement> list = reimbursementService
        .listByDateRange(LocalDate.now().minusDays(1), LocalDate.now());

    // 2. 逐条匹配规则
    for (Reimbursement r : list) {
        List<AbnormalHit> hits = abnormalRuleEngine.check(r);
        if (!hits.isEmpty()) {
            // 3. 写入 abnormal_record
            abnormalRecordService.batchSave(r.getId(), hits);
            // 4. AI生成摘要
            String summary = aiService.generateAbnormalSummary(r, hits);
            // 5. 推送消息
            notifyService.pushToFinance(r, hits, summary);
        }
    }
}
```

## 四、文件存储——MinIO 最佳实践

### 4.1 目录结构

```
bucket: expense-invoices
├── raw/           ← 原始上传文件（永久保留）
│   └── {userId}/{yyyyMM}/{uuid}.{ext}
├── thumb/         ← 缩略图（200x200，前端预览用）
│   └── {userId}/{yyyyMM}/{uuid}_thumb.jpg
└── temp/          ← 临时文件（24小时自动清理）
    └── {sessionId}/{uuid}.{ext}
```

### 4.2 签名URL生成

```java
public String generatePresignedUrl(String objectName) {
    return minioClient.getPresignedObjectUrl(
        GetPresignedObjectUrlArgs.builder()
            .bucket("expense-invoices")
            .object(objectName)
            .method(Method.GET)
            .expiry(5, TimeUnit.MINUTES)  // 5分钟有效
            .build()
    );
}
```

### 4.3 文件清理策略

```
- temp/ 目录：MinIO Bucket Lifecycle 规则，24小时自动过期
- raw/ 目录：永久保留（合规要求），但6个月后可转冷存储
- thumb/ 目录：与 raw/ 同步生命周期
```

## 五、AI 调用——统一封装层

### 5.1 AiService 核心设计

```java
@Service
public class AiServiceImpl implements AiService {

    // 三层缓存
    // L1: 本地 Caffeine（1分钟） → L2: Redis（24小时） → L3: 调用API

    @Override
    @Cacheable(value = "ai:invoice:summary", key = "#invoice.id")
    @RateLimiter(name = "ai-call", max = 10, window = "1m")
    public String generateInvoiceSummary(Invoice invoice) {
        String prompt = promptTemplateEngine.render("invoice/summary", invoice);
        try {
            return deepSeekClient.chat(prompt);
        } catch (Exception e) {
            log.warn("AI摘要生成失败，使用默认文案", e);
            return buildDefaultSummary(invoice); // 降级
        }
    }
}
```

## 六、安全加固清单

| 层面 | 具体措施 | 优先级 |
|------|----------|--------|
| SQL注入 | MyBatis-Plus 参数化查询（#{}用得多），禁${} | P0 |

| 密码策略 | BCrypt加密、最小8位、支持密码过期 | P2 |

## 七、性能优化备忘

| 优化点 | 措施 | 预期效果 |
|--------|------|----------|
| 发票列表查询 | 联合索引 idx_trip_id + idx_type_date | 100ms → 20ms |
| 审批流查询 | Camunda 历史表索引 + 定期归档 | 保持稳定 |
| OCR调用 | 异步处理（CompletableFuture），先返回"识别中" | 用户等待感降低 |
| 图片加载 | 缩略图+CDN（Nginx缓存），不加载原图 | 3MB → 50KB |
| 数据库连接池 | HikariCP，最大连接数20 | 避免连接耗尽 |
| Redis序列化 | 用Protostuff替代JDK序列化 | 内存减半 |
