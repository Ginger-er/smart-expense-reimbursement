# 面试准备手册 —— 智能差旅报销系统

> 项目做精不做多。核心3个模块做透，准备好"遇问题→解决"的故事，比背技术点重要10倍。

---

## 一、项目介绍话术

### 2分钟电梯演讲版

> "我独立开发了一个智能差旅报销系统，解决企业员工报销流程繁琐、财务审核效率低的问题。
>
> 核心功能有三个：
>
> **第一，发票智能识别。**用户拍照上传后，调用百度OCR提取发票信息，后端做五次校验——金额一致性、日期有效性、发票代码校验位、重复报销检测、关联合理性。识别准确率95%以上，识别失败自动降级为手动填写。
>
> **第二，智能审批流。**我用 Camunda BPMN 引擎设计了多级审批流程，根据报销金额自动判断审批层级——1000以内直属领导审批即可，1000到5000走两级，5000以上走三级审批。支持会签、转办、驳回后重新提交，状态变化全程留痕。
>
> **第三，费用异常预警。**用 XXL-Job 每天9点定时扫描，匹配五条异常规则——金额突增、限额擦边、重复发票、日期异常、高频报销——命中后调用 DeepSeek 生成预警摘要推送给财务管理员。
>
> 技术栈是 Spring Boot 3 + Vue3 + Camunda + Redis + XXL-Job，前后端分离部署。从数据库设计到部署上线，完整8周迭代。"

### 30秒一句话版

> "我做了一个智能报销系统，拍照上传发票AI自动识别，提交后按金额自动走多级审批，每天扫描异常推送给财务——用的Spring Boot + Camunda + OCR。"

## 二、高频面试问题逐题攻破

### Q1："发票OCR识别失败了怎么办？"

**面试官考察点**：你有没有考虑容错和用户体验

**回答框架**（3层降级）：

> "我设计了三层降级方案。
>
> **第一层——用户层面**：识别失败时，前端直接展示手动填写表单，让用户录入发票信息。不会因为AI挂了就阻塞用户流程。同时记录失败日志，后续排查原因。
>
> **第二层——服务层面**：如果某个OCR供应商持续失败（比如错误率超过30%），我会在配置层切换到备用供应商。我设计时抽象了 OcrProvider 接口，百度OCR和腾讯云OCR都是实现类，配置切换即可。
>
> **第三层——事后补救**：所有OCR识别结果都保存了原始JSON留痕在数据库，财务复核时可以对比原始图片和识别结果，人工修正后状态标记为'人工修正'。
>
> 还有一个细节——识别中前端展示loading，超过5秒就提示'识别较慢，请稍候'，避免用户焦虑。"

### Q2："高并发下报销额度扣减怎么保证安全？"

**面试官考察点**：分布式并发控制

**回答框架**（按复杂度递进）：

> "这个问题核心是防止同一个预算被两次扣减。我的方案有两层：
>
> **常规场景用数据库乐观锁**。预算表加一个 version 字段，更新时 `WHERE version = ? AND remaining >= ?`，如果 affected rows = 0 说明被其他请求改了，触发重试。大部分并发不高时这就够了。
>
> **如果并发量大**，用 Redis 分布式锁（Redisson 的 RLock）。锁的粒度是'出差申请ID'，不是全局锁，避免锁冲突。加锁时设置超时时间防止死锁。
>
> 还有一个思路——如果预算扣减不是强实时需求，可以用 Redis 的 INCRBY 做预扣，异步同步到数据库，性能更好。
>
> 你觉得哪种更合适你这个场景？——这说明你理解不同方案的适用场景。"

### Q3："审批流驳回后重新提交，状态怎么设计？"

**面试官考察点**：状态机设计、数据完整性

**回答框架**：

> "我的状态机设计是这样的：
>
> 驳回后状态回到'草稿'(0)，员工修改后重新提交，状态经过'待审批'(1)→'审批中'(2)→'已通过'(3)或再次'已驳回'(4)。
>
> 关键设计有两个：
>
> **第一，历史审批记录保留不删**。approval_record 表每个节点都记录一条，包含审批人、动作、意见、时间。驳回后重新提交时，新审批记录追加写入，前端展示时显示'第2次提交'，历史审批可见。这样审计追溯完整。
>
> **第二，Camunda 流程实例的处理**。驳回时我会 `deleteProcessInstance` 终止当前 Camunda 流程实例，重新提交时启动新实例。而不是用 Camunda 的回退机制——因为回退后流程变量状态难以完全重置，容易出 bug。终止+重启更干净。
>
> 还有一个细节——驳回原因是必填的，字段设了 NOT NULL 或前端校验，防止'无故驳回'。"

### Q4："AI生成的内容 hallucination 怎么办？"

**面试官考察点**：AI工程化能力

**回答框架**：

> "hallucination 是 AI 集成绕不开的问题，我做了三层防护：
>
> **第一层——输入约束**。提示词写得非常具体。比如发票摘要，我限定了角色、任务、输入字段、输出格式、字数限制，还给了示例。越具体的提示词，幻觉越少。
>
> **第二层——输后处理校验**。AI返回的结果我会做规则校验：金额不能为负数、发票类型必须在1-4枚举范围内、摘要长度不超过50字。校验不通过就丢弃，用预设的模板文案替代。比如'餐饮发票¥186.00'这种简单拼接，至少不会出错。
>
> **第三层——降级兜底**。如果DeepSeek API完全挂了（超时、限流、返回异常），整个AI调用被 try-catch 包裹，异常时返回默认文案，不会影响主流程。
>
> 我还设计了一个 ai_invoke_log 表记录每次调用的输入输出，方便后续抽样评估质量、优化提示词。这其实是MLOps的思路。"

### Q5："用户量大了怎么扩展？"

**面试官考察点**：架构思维

**回答框架**：

> "扩展性我是从设计阶段就考虑的：
>
> **应用层**：Spring Boot 应用本身就是无状态设计（session 存在 Redis），所以可以直接水平扩展——加服务器、前面挂 Nginx 负载均衡就行。
>
> **数据库**：MySQL 做读写分离，读多写少的场景（比如报销列表查询）走从库。热点数据（比如费用标准、用户信息）缓存到 Redis，减少 DB 压力。
>
> **文件存储**：发票图片存在 MinIO（S3兼容），和应用服务器解耦。MinIO 本身支持分布式部署，可以横向扩展。
>
> **任务调度**：XXL-Job 本身是分布式的，执行器可以注册多个，调度中心自动分片，不会单点。
>
> 如果用户量真的上百万，还可以考虑——报销单按月份分表、搜索走 ES、消息队列削峰（比如批量报销审批通知用 RocketMQ）。
>
> 不过说实话，报销系统不是高并发场景——一个公司几千人，每天报销提交QPS可能就几十。过度设计反而不划算。我现在的架构已经够用了。"

### Q6："Camunda 和普通状态机有什么区别？"

**面试官考察点**：技术选型理解

**回答框架**：

> "普通状态机——比如用枚举+if-else写——适合简单固定的流程。但报销审批流程有几个特点让它不适合硬编码：
>
> **第一，条件分支复杂**。金额决定审批层级、超预算需额外加签、某些部门走特殊流程……这些如果硬编码会很乱。
>
> **第二，流程可视化**。Camunda 的 BPMN 图业务人员和开发可以一起看，审批流程长什么样一目了然。
>
> **第三，高级特性**。会签（多个审批人都通过才过）、或签（任一人通过即可）、超时自动提醒、历史流程查询——这些都是 Camunda 内置的，自己写状态机得写很多代码。
>
> **第四，变更友好**。如果公司组织架构变了——比如审批层级从3级改成4级——Camunda 改 BPMN 图就行，不用改代码逻辑。
>
> 当然，Camunda 学习成本高，如果审批流非常简单（就一级审批），没必要上。但报销系统的场景确实适合。"

### Q7："这个项目遇到的最大困难是什么？"

**面试官考察点**：解决问题的能力 + 故事讲述能力

**STAR法则准备**：

> **S (Situation)**：
> "在做 Camunda 审批流集成的时候，遇到了一个棘手的问题——驳回后重新提交，流程状态混乱。"
>
> **T (Task)**：
> "审批流有三层：直属领导→部门经理→财务总监。如果直属领导通过了，部门经理驳回了——员工修改后重新提交——这时候流程该从哪个节点开始？Camunda 默认的流程回退会保留之前的流程变量，导致判断条件不准确。"
>
> **A (Action)**：
> "我研究了几种方案：
> 1. Camunda 的回退 API——发现流程变量状态不好清理
> 2. 跳过已完成的节点——但逻辑复杂
> 3. 终止旧实例 + 启动新实例——最干净
>
> 我选择了方案3。驳回时调用 `runtimeService.deleteProcessInstance()` 终止当前实例，重新提交时重新启动流程。但保留所有历史审批记录在 approval_record 表中，前端显示'第N次提交'。
>
> 这个方案有个边界——如果部门经理通过了，财务总监驳回了，重新提交后前面两个节点不应该重新审批。我加了 skipPrevious 标记位，重新启动时自动跳过已通过的节点。"
>
> **R (Result)**：
> "最终方案跑得很稳，驳回→修改→重提、反复3次都能正确流转。这个踩坑经历让我对 Camunda 的生命周期管理理解深了很多。"

## 三、技术深度追问准备

### 追问："MyBatis-Plus 和 JPA 怎么选的？"

> "报销系统有大量复杂查询——比如'查询某员工某月某类型的发票合计'、'按多个状态筛选报销单'——这种场景 MyBatis-Plus 写 SQL 更灵活。JPA 的命名查询写复杂查询方法名会很长。而且团队熟悉 MyBatis，上手成本低。但 MyBatis-Plus 的代码生成器能自动生成 Entity/Mapper/Service，写 CRUD 基本不用手写——这比 JPA 的约定优于配置更省代码。"

### 追问："Redis 在你项目里用了哪些地方？"

> "三个场景：
> 1. **Session 共享**——Sa-Token 把登录态存在 Redis，应用多实例时session不丢
> 2. **AI调用限流**——用 Redis 的滑动窗口记录每个用户每分钟AI调用次数，超了返回'请稍后再试'
> 3. **热点数据缓存**——费用标准、部门列表这些变更少查询多的数据，缓存后接口从 80ms 降到 5ms"

### 追问："MinIO 的签名URL是怎么设计的？"

> "发票图片存在私有 Bucket，不能直接通过URL访问。用户请求图片时，后端生成带签名的临时URL——有效期5分钟——签名用的 SecretKey 只有服务端知道。过期后URL自动失效，别人拿到URL也不能访问。这个机制类似AWS S3的 Pre-signed URL。"
