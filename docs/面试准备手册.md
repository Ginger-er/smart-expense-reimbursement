## 一、项目介绍话术

### 2分钟电梯演讲版

> "我独立开发了一个企业差旅报销系统，覆盖「出差申请 → 发票上传识别 → 报销单提交 → 多级审批 → 财务打款」全流程。
>
> 核心亮点有三个：
>
> **第一，发票智能识别。**用户拍照上传后，后端异步调用百度 OCR 识别（增值税发票识别失败会自动降级到智能票据识别，火车票/行程单也能认），前端轮询识别结果，识别失败可直接人工填写，全程留痕。上传接口立即返回，不被识别耗时阻塞。
>
> **第二，多级审批 + 并发防护。**审批是手写状态机——0草稿/1待审批/2审批中/3已通过/4已驳回/5已打款，金额 ≥5000 自动走两级审批（领导→财务），小额财务/管理员终审直接通过。提交用 Redis SETNX 做幂等防重复，审批和打款用 Redis 分布式锁串行化，打款另外叠加数据库乐观更新 `WHERE status=3` 做双层防护。还修掉了自审自批漏洞——任何角色都不能审批自己提交的单据。
>
> **第三，数据报表 + 缓存。**工作台和报表页背后是十几条聚合 SQL（GROUP BY + JOIN），结果按角色/数据范围缓存在 Redis（5 分钟 TTL），Redis 故障自动降级直查数据库，业务不中断。附带操作日志 AOP、站内通知、EasyExcel 导出。
>
> 技术栈 Spring Boot 3 + MyBatis-Plus + Sa-Token(JWT+Redis) + MySQL + Redis + Vue3 + TypeScript，四级角色权限隔离，Docker Compose 一键部署，60 个单元测试。"

### 30秒一句话版

> "我做了一个差旅报销系统：拍照上传发票 OCR 自动识别，提交后按金额走两级审批，Redis 分布式锁 + 数据库乐观锁防并发重复打款，统计报表带缓存——Spring Boot 3 + Vue3 + Sa-Token + Redis。"

## 二、高频面试问题逐题攻破

### Q1："发票OCR识别失败了怎么办？"

**面试官考察点**：有没有考虑容错和用户体验

**回答框架**（真实的三层降级）：

> "我设计了三层降级。
>
> **第一层——识别链路内部降级**：先调增值税发票识别，失败自动转智能票据识别接口（火车票、行程单、定额发票），两类票据都能覆盖。
>
> **第二层——人工兜底**：还是失败，发票 ocr_status 标记为失败，前端提示用户手动填写表单，不会阻塞报销流程。所有原始识别 JSON 都留痕在数据库，财务复核时可以对比图片和识别结果。
>
> **第三层——异步不阻塞**：识别在后台线程池里执行，上传接口立即返回，前端轮询识别状态，用户不用盯着页面等。线程池用 CallerRunsPolicy 拒绝策略——队列满了由调用线程执行，保证任务不丢。"
>
> （代码位置：`OcrAsyncTask` / `InvoiceServiceImpl.ocrRecognize` / `AsyncConfig`）

### Q2："高并发下审批/打款怎么保证安全？"

**面试官考察点**：分布式并发控制

**回答框架**（本项目真实的三层防护）：

> "三个场景三种方案，按冲突风险递进：
>
> **提交幂等**：员工双击提交按钮或网络重试，用 Redis SETNX 抢占 `idem:submit:{id}` 标记，10 秒 TTL，finally 里立即释放。拿不到标记说明有请求在提交，直接提示'请勿重复提交'。Redis 挂了怎么办？降级放行，由第三层状态机校验兜底——只有草稿/已驳回状态才能提交。
>
> **审批防双写**：审批是'校验 → 插审批记录 → 改状态'的复合操作，两个并发请求（比如领导通过和财务驳回同时点）会插出两条审批记录、状态互相覆盖。我把整个审批操作包在 `executeWithLock` 里——SETNX+EX 原子加锁、UUID 做持有者标识、Lua 脚本校验 value 一致才删除（防止 A 的锁过期后被 B 抢到、A 再解锁把 B 的锁删了）。拿不到锁直接快速失败。
>
> **打款双层防护**：第一层同样用分布式锁串行化；第二层保留数据库乐观更新——`UPDATE reimbursement SET status=5 ... WHERE id=? AND status=3`，affected rows 为 0 就抛业务异常。即使锁失效（Redis 宕机、锁过期），DB 这层依然挡住重复打款。
>
> 为什么不用 Redisson？项目体量小，手写 SETNX+Lua 几十行就够，而且我理解底层原理；如果以后要可重入、自动续期（看门狗），再引入 Redisson 也不迟。"

### Q3："审批流驳回后重新提交，状态怎么设计？"

**面试官考察点**：状态机设计、数据完整性

**回答框架**：

> "我的状态机是：0草稿 → 1待审批 → (≥5000)2审批中 → 3已通过 → 5已打款；任一审批节点可 →4已驳回。
>
> 关键设计有三个：
>
> **第一，驳回不是死路**。已驳回的单据可以重新提交（报销单直接重提、出差单可先修改再重提），重新提交时金额重新归集、清空上次驳回原因，回到待审批状态。
>
> **第二，历史审批记录保留不删**。approval_record 表每个节点记录一条——审批人、动作、意见、时间。重新提交后新记录追加写入，前端详情页按时间轴展示，审计追溯完整。
>
> **第三，状态校验都在服务端**。每个流转操作都先校验当前状态才放行，比如只有'已通过'才能打款。状态码是唯一事实来源，不信任前端传来的任何状态字段——出差单更新接口用字段白名单，客户端传 status 会被直接忽略。"
>
> （这是我修过的真实 bug：早期版本出差单更新用 `updateById` 全字段覆盖，客户端可以直接把状态改成'已通过'跳过审批。）

### Q4："为什么用异步而不是同步做 OCR？"

**面试官考察点**：异步化思维

**回答框架**：

> "OCR 调用要 2~5 秒，如果同步做，用户上传后干等，HTTP 连接一直被占着，高并发下线程资源很快耗尽。
>
> 改成异步：上传接口落库后立即返回，`@Async("ocrExecutor")` 在专用线程池（core 2 / max 4 / 队列 100）里执行识别，前端轮询识别状态展示结果。
>
> 两个容易追问的点：
> 1. **拒绝策略**选 CallerRunsPolicy——队列满了由提交线程自己执行，宁可让上传接口慢一点也不丢任务；
> 2. **线程池隔离**——OCR 是 IO 密集操作，和业务线程池分开配置，避免互相拖累。"
>
> （代码位置：`AsyncConfig` / `OcrAsyncTask` / `InvoiceController.upload`）

### Q5："用户量大了怎么扩展？"

**面试官考察点**：架构思维 + 诚实度

**回答框架**：

> "应用层无状态（登录态在 Redis），加实例挂 Nginx 负载均衡就能水平扩展，分布式锁保证多实例下审批/打款依然安全。
>
> 数据库：读多写少，可以读写分离，统计类查询结果已经在 Redis 缓存（5 分钟 TTL），DB 压力不大。
>
> 文件存储：当前是本地磁盘（演示项目够用），生产应该换 MinIO/OSS——这是我明说的演进方向，代码里文件路径是配置项，迁移成本可控。
>
> 不过说实话，报销系统不是高并发场景——一个公司几千人，QPS 几十。过度设计反而不划算。我优先把并发正确性（锁+乐观锁）和降级（Redis 故障回源 DB）做扎实了。"

### Q6："为什么不用工作流引擎（Camunda/Flowable）？"

**面试官考察点**：技术选型的判断力（**别吹自己没用的东西，被追问必穿帮**）

**回答框架**：

> "我评估过，结论是当前场景不需要。
>
> 报销审批的核心就一句话：金额 ≥5000 走两级（领导→财务），否则一级终审。用状态码 + if-else 就能表达，引入 Camunda 要学 BPMN、部署引擎、处理流程变量的生命周期，复杂度收益不成比例。
>
> 但我不是把状态写死了——审批记录表 approval_record 每条带节点名和审批人，将来如果要会签/转办/动态路由，可以在状态机上加扩展，或者到那个复杂度再引入引擎，迁移点很清楚。
>
> 选型原则：先用最简单的方案解决当前问题，为可预见的扩展留好口子。"

### Q7："这个项目遇到的最大困难是什么？"

**面试官考察点**：解决问题的能力 + 故事讲述能力

**STAR法则准备**（真实故事，代码里可指认）：

> **S (Situation)**：
> "我给自己项目做代码审查时，发现一个隐蔽的权限漏洞——审批接口只校验了'领导只能审本部门'，没有校验'审批人不是申请人本人'。这意味着一个领导提交报销单后，可以自己给自己审批通过，然后财务打款——整个审批流形同虚设。"
>
> **T (Task)**：
> "需要堵住自审自批，而且要覆盖报销单和出差单两条链路，同时不能影响正常的跨级审批。"
>
> **A (Action)**：
> "在审批入口加了统一的守卫：当前登录人 == 单据归属人时直接抛业务异常。然后补了单元测试固定这个行为——'领导审自己的单必须抛异常'。顺手把同类问题也排查了：发票详情接口的越权查看（IDOR）、出差单更新的状态篡改，都在同一轮修掉了，每个修复都配了测试。"
>
> **R (Result)**：
> "审批链路的职责分离真正闭环：申请、审批、打款三种角色互斥。这件事让我养成习惯——写完每个写接口，都从'如果我是一个想钻空子的用户'的角度过一遍。"

## 三、技术深度追问准备

### 追问："MyBatis-Plus 和 JPA 怎么选的？"

> "报销系统有大量复杂查询——按状态/关键字/日期范围筛报销单、按部门分组统计、费用类型分布——MyBatis-Plus 写 SQL 灵活直观。代码生成器能自动生成 Entity/Mapper/Service，CRUD 基本不用手写。JPA 的命名查询写复杂查询方法名会很长，而且复杂关联的 N+1 问题要花心思。团队的熟悉度也是考虑因素。"

### 追问："Redis 在你项目里用了哪些地方？"

> "三处，职责分开：
> 1. **会话存储**——Sa-Token 把登录态存 Redis，应用无状态可水平扩展，禁用用户还能立即踢下线；
> 2. **分布式锁 + 幂等标记**——审批/打款防并发、提交防重复，SETNX+EX 加锁、UUID 标识持有者、Lua 脚本原子释放；
> 3. **统计缓存**——工作台/报表的聚合查询结果缓存 5 分钟，key 里带上角色/用户/部门/日期范围，保证不同数据范围互不串数据；Redis 读写异常全部降级直查数据库，缓存故障不影响业务。"

### 追问："统计缓存怎么防穿透/击穿/雪崩？"

> "诚实说：统计类数据对一致性要求低，我做了简化取舍。
>
> **穿透**：查询的 key 空间只来自真实登录用户和真实日期范围，不存在恶意构造不存在的 key 打穿缓存的场景，所以没做空值缓存。
>
> **击穿**：热点 key 失效瞬间的并发重建——单次聚合查询在毫秒级，重建成本低，加互斥锁的收益不大，先不加。
>
> **雪崩**：所有 key TTL 统一 5 分钟，但因为每个 key 的写入时刻由用户首次访问决定、天然分散，不会同一秒集体过期。
>
> 真正重要的是**降级**：Redis 读失败、写失败、反序列化失败，全部 try-catch 回源数据库，业务永不因缓存故障中断。先简单后优化——如果以后报表查询变慢，再加互斥重建和随机 TTL。"

### 追问："打款为什么用分布式锁 + 乐观锁两层？"

> "两层各司其职：分布式锁挡住并发请求的重复执行，乐观更新是数据层的最终防线——`WHERE status=3` 保证只有第一笔更新成功。
>
> 只靠锁的风险：Redis 宕机时锁降级放行，或者锁意外过期，两个请求都可能走到更新语句；只靠乐观锁的话，第二个请求会拿到'只有已通过的报销单才能打款'的报错——结果正确，但锁让大多数重复请求在前置就被友好拦截。
>
> 原则：分布式锁优化体验和吞吐，数据库约束保证正确性。数据库是最后一道防线。"

### 追问："文件存储为什么用本地磁盘？"

> "演示项目图省事，生产不能这么干。发票图片存在应用本地目录，多实例部署时 A 实例上传的图片 B 实例读不到——这正是我扩展性章节里说'生产换 MinIO/OSS'的原因。文件路径是配置项（`app.upload-dir`），迁移时改配置 + 换存储实现即可。"
